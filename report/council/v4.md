# Section 8 — Which recommendation strategy would you select for this platform, and why?

## 8.1 What the metric actually asks for

The organisers' target is not "things the user watched." It is: take every view with
screen time (watched duration / programme duration) **≥ 0.8**, count how often each
programme recurs at that completion level, and keep the **strictly five** most frequent,
in descending order — order matters, and the score's denominator is `min(5, |relevant|)`.
Under this rule `|R| = 5` for 90.9% of users, including both users examined below, so the
denominator is fixed at 5 for almost the whole test set: this metric does not reward
recall over a long tail, it rewards identifying — and ranking first — a user's small,
closed set of habitual, fully-watched programmes.

Two consequences follow directly, and both are visible below. First, because order
matters, a list with the right items in the wrong order scores far below the same items
placed earlier — the specification's worked examples show a 3.4-point swing (0.9167 vs
0.5333) from reordering five identical hits. Second, because "relevant" means *frequent
and complete*, a programme a user watches constantly but never finishes is not relevant
at all — so a method that recommends a user's objectively most-watched programme can
score zero, not because the recommendation was unreasonable but because raw frequency
and "top-5 frequent-at-high-completion" are different quantities. This is what the top-5
restriction being worth +0.0079 hold-out (eight times the seed spread) is measuring:
restricting to five changes which programmes count, independently of the ranking model.

## 8.2 The two users, scored against this definition

HEAVY (3,733 history events, 445 distinct programmes) and LIGHT (1 history event, 1
distinct programme) both have exactly 5 relevant programmes in the hold-out window.
Section 7 records each method's top-5 with hit/miss per rank; applying the brief's own
AP@5 formula to those exact rank positions gives:

| method | HEAVY hit ranks | HEAVY AP@5 | LIGHT hit ranks | LIGHT AP@5 |
| --- | --- | ---: | --- | ---: |
| popularity | 2 | 0.100 | 2,3,4 | 0.383 |
| association rules | 2 | 0.100 | 2,3,4 | 0.383 |
| PageRank (PPR) | 2 | 0.100 | 3,4,5 | 0.287 |
| content-based (CBF) | 4 | 0.050 | — | 0.000 |
| matrix factorization (iALS) | — | 0.000 | — | 0.000 |
| FINAL (LambdaRank, 41 feats) | 1 | 0.200 | 1,2,5 | 0.520 |

The hit *count* reported in Section 7 (1/5 for most HEAVY lists, 3/5 for most LIGHT
lists) hides exactly the effect the metric is built to punish or reward: popularity, AR
and PPR tie on hit count for LIGHT (3/5 each) but PPR scores 25% lower (0.287 vs 0.383)
purely because its hits land one rank later on average. FINAL wins on both users not by
finding more relevant items than popularity (same hit count for HEAVY, same count for
LIGHT as popularity/AR) but by placing them earlier — the entire LambdaRank advantage
visible here is a ranking effect, consistent with the hold-out finding that the gap to
the candidate-pool ceiling, not candidate coverage, is the project's bottleneck.

The clearest "sensible recommendation, zero score" case is HEAVY's own top-watched
programme, id 2400480 ('ТСН. Неделя', 538 views in the training window — by far this
user's most frequent item). Every method, including FINAL, ranks it in its top two, and
every method is wrong: it is a miss everywhere. A programme watched 538 times is not
automatically one of this user's five most-*frequent-at-high-completion* programmes in
the target window — habits can diverge between windows, and frequent partial viewing
(frac < 0.8) never enters the qualifying set at all. No method here recovers from this;
it is evidence that the top-5/high-completion definition, not model quality, determines
a large share of what scores.

## 8.3 Why the methods diverge

Familiar vs. new: every hit for both users is a generic, high-reach "Інфо" programme
(news bulletins, daily digests) already near-universal across the user base. CBF and
iALS, by contrast, each propose thematically coherent but wrong lists — HEAVY's iALS
suggests serials ('Отдел 44', 'Отчаянные домохозяйки') content-adjacent to what the user
actually watches (the user's history includes a children's cartoon and daytime info), and
LIGHT's CBF proposes serials content-similar to the one watched film ('Призрак'). Both
score zero. This is the brief's caution made concrete: an unfamiliar list is not evidence
of useful discovery, only of a miss against this target — nothing here says whether the
user would have enjoyed 'Отдел 44'; it says only that it was not among their five most
frequent, fully-watched programmes in this window.

Association rules and PageRank, for HEAVY, produce the *identical* ranked list to raw
popularity. With 445 distinct programmes behind the user, personalised co-occurrence and
graph diffusion have nothing left to add beyond the population baseline — the signal
collapses onto the same few near-universal items. For LIGHT, with only one seed item,
PPR's diffusion starts from that single film before reaching the popular info
programmes, which reorders (and, per §8.2, costs) the list relative to plain popularity;
AR with one seed item still reproduces popularity exactly, since its one co-occurrence
row is dominated by the same generic items. Content attributes (CBF) are the only method
that engages meaningfully when co-view signal is this thin — it needs no interaction
graph — but engaging is not the same as being right: for LIGHT it returns five serials,
none of which are the actual five high-completion programmes, all unrelated news
bulletins. Popularity already does well for LIGHT (0.383, matching AR) precisely because
the true target regresses toward a small set of nationally habitual info programmes
regardless of a thin individual history, which is also why "no cold-start problem" holds
here: a near-empty history does not prevent five fully-watched, predictable programmes
in the next window.

## 8.4 The strategy selected, and why

The shipped configuration — LambdaRank over 41 features, rank-averaged over 5 seeds,
1600 trees — is the strategy to deploy: hold-out 0.43949 ± 0.00095 against the true
target, and the designated Kaggle submission (`sub25_top5_s0`) scores private 0.44205,
above the frozen leaderboard's first place (private 0.42912). On the two users above it
is also the only method that outperforms popularity on both, without exception. The
alternatives tried and rejected confirm this is not a close call at this scale: cascade
re-ranking over the top 20 cost −0.0064 hold-out; rank fusion of six LightGBM variants
scored private 0.43419–0.43422 (below the single model), because the variants already
agree on 5.86 of 5 items on average — there is nothing to fuse, only extra compute; the
LightGBM+CatBoost fusion, the most genuinely different pairing tried, still lost at
private 0.43405. Given the deployment hardware (an 8 GB, fanless M1 that supports one
heavy LightGBM job at a time), a single 1600-tree ranker is also the only one of these
options that is cheap enough to retrain regularly; ensembling buys nothing and costs a
multiple of the training time. For the user experience, the practical implication of
§8.2–8.3 is that this strategy's lists will skew toward a user's own high-reach daily
habits rather than toward novel titles — appropriate for a metric built around repeat,
completed viewing, but it means this strategy alone should not be read as an answer to
whether users would value more exploratory recommendations, which this data cannot speak to.

## 8.5 Limitations and failure cases this data actually supports

Only 10.8% of schedule rows carry a `tv_show_id`; the remaining 89.2% of airtime can
never become a recommendable item, independent of any model. Under the true target the
candidate pool (139/user) reaches recall 0.8181 and a MAP@5 ceiling of 0.8181 — 18.2% of
users' true top-5 programmes are structurally unreachable before ranking even starts, and
17.1% of correct answers are missing from the pool outright, 175 of them premieres that
cannot be predicted from past viewing by construction. The attempted fix for `|R| < 5`
users (group weight = 1/min(5, positives)) is void rather than merely rejected, because
|R| = 5 for 90.9% of users leaves nothing to normalise. Finally, the public score is
systematically above the private score for every model measured, including the
leaderboard leader's, so a single submission's public figure should not be read as the
platform-facing number. None of this licenses a claim about user satisfaction, engagement,
or revenue — no online experiment was run, and the view log records only what this
platform observed, not a complete record of what any user has "never" or "always" watched.
